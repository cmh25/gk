# gk v4 release notes

## exact floating point

v4 makes one change, and it is semantic: **floating-point tolerance is removed**.
Every float operation now returns the exact IEEE 754 result — the same answers
as C or Python. Nothing else changes in v4.

Through v3, gk followed classic k practice: `=`, `<`, `>`, and `~` compared
floats with a relative tolerance of about 1e-13, and floor `_` (and through it
float mod `!`) snapped a value to an integer it was tolerantly equal to.

```
  2=1.9999999999999        / v3: 1     v4: 0
  _1.9999999999999         / v3: 2     v4: 1
  1.8!0.2                  / v3: 0     v4: 0.2  (0.19999999999999996)
```

### why

1. **64-bit reach.** The tolerance is relative (~1e-13·|x|), so past ~2.5e12 the
   slack spans whole integers, and tolerant floor corrupted exact values that
   are ordinary working magnitudes now that gk has 64-bit longs:

   ```
     _100000000000007.0     / v3: 100000000000008j (!)   v4: 100000000000007j
     100000000000007.0!10.0 / v3: -3.0 (!)               v4: 7.0
   ```

2. **Consistency.** The hashed verbs (find `?`, `in`, distinct, group) and float
   grade were always exact, so the language disagreed with itself: `~` could say
   two values match while `?` said one is not found and distinct kept both. Now
   every verb gives the same verdict.

3. **Soundness.** A tolerant comparator is not transitive (a≈b and b≈c do not
   imply a≈c), so it never defined a consistent ordering for sort and grade.

### what this means in practice

The classic floating-point round-off that tolerance used to paper over is now
visible, exactly as in C or Python:

```
  (0.1+0.2)=0.3            / 0    (0.1+0.2 is 0.30000000000000004)
  _100*0.29                / 28   (100*0.29 is 28.999999999999996)
  ((sqrt 2.0)*sqrt 2.0)=2.0    / 0
```

- Compare computed floats with explicit slack, not `=` or `~`:

  ```
    1e-9>abs x-y
  ```

- Round to nearest with `_0.5+x` when you mean nearest, not floor.

- f32 vs f64: only exactly-representable values compare equal across widths
  (`2.5e=2.5` → 1, but `0.1e=0.1` → 0, since the f32 and f64 roundings of 0.1
  are different numbers). Compare within one width, or with slack.

- Float mod is exact `fmod` (still signed by the divisor): `1.8!0.2` is
  `0.19999999999999996` because the stored `0.2` does not evenly divide the
  stored `1.8` — the true quotient is 8.99999999999999972…, not 9. Python's
  `1.8 % 0.2` agrees.

Integer results are untouched: everything over ints and longs — including int
mod, `div`, and comparisons — was always exact and stays so.
