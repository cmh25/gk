## Part I — Behavior changes

*These change what working code does.*

### Types, literals, and printing



<a id="neg-zero"></a>

#### negative zero prints

IEEE floats carry a signed zero, and gk now prints it. Only the rendering
changed: `-0.0` still compares *equal* to `0.0` under `=`/`<`/`>`/`~` and sorts
and groups with it.

```
  -0.0                     / v4: 0.0      v5: -0.0
  0.0*-1.0                 / v4: 0.0      v5: -0.0
  ceil -0.1                / v4: 0.0      v5: -0.0
```

gk already believed in signed zero everywhere else (`$-0.0` was `"-0"`, `1%-0.0`
was `-0i`), so the printer was the one place it was denied — and that denial was
also hiding two real bugs (below). A negative zero now carries its own `.0` so
every form round-trips (`1.5 -0.0 2.5`); `\zc` still folds noise to `+0.0` but no
longer erases an exact `-0.0`.

---



<a id="j-mix"></a>

#### `j` cannot be mixed with a float in a literal

An unsuffixed token takes the vector's width, so a literal's type is not settled
until its end or first suffix — that flexibility stays (`1 2 3j` and `2j 3 4`
are i64; `1.0 2 3.0e` is f32). But a `j` suffix asserts i64, and no float vector
can hold one, so mixing `j` with **any** float token — decimal, exponent,
`e`-suffixed, or float sentinel — is now a `parse` error instead of a silent
promotion that dropped the suffix:

```
  1j 2.0                   / v4: 1 2.0     v5: parse error
  0n 2j                    / v4: 0n 2      v5: parse error
```

Write a list when you mean one (`(1j;2.0)`). Int nulls and infinities are
unsuffixed and adopt like any int (`0N 2j` is i64, `0N 2.0e` is f32); the float
sentinels are typed (`0n`/`0i` f64, `0ne`/`0ie` f32).

---



<a id="sentinels"></a>

#### the `i64`/`f32` sentinels adopt, widen, and wrap

The `i64`/`f32` types carry the same null/infinity sentinels as i32/f64
(`0Nj`/`0Ij`, `0ne`/`0ie`), but three cross-type rules the older types obeyed
did not hold for them. All three are fixed:

- **Adopt** — an unsuffixed sentinel takes the vector's width: `0N 0I 2j` is
`0Nj 0Ij 2j` (was `0Nj 2147483647 2j`).
- **Widen** — a narrow→wide conversion maps the sentinel across, not its bit
pattern: `0N+1j` is `0Nj` (was `-2147483647j`), `0N+0.0e` is `0ne`.
- **Wrap** — integer `0N`/`0I` are `INT_MIN`-family bit patterns, not NaN, so
they still wrap in integer arithmetic as in i32: `0I+1j` is `0Nj` (== `0Ij+1j`),
not `2147483648j`.

Only the *float* nulls are NaN and propagate; adding zero across a widen leaves
the sentinel unchanged (`0N+0j` is `0Nj`, was `-2147483648j`).

<a id="f32-print"></a>

#### `f32` prints enough digits to round-trip

An `f32` now prints up to nine significant digits under `\p` (`FLT_DECIMAL_DIG`),
so `. 5:x` reparses to the same value; it was capped at seven. The default `\p 7`
is unchanged.

```
  \p 9
  5:1.0000001e             / v4: "1.0e" (lost on reparse)   v5: "1.00000012e"
```



<a id="f32-lex"></a>

#### an `e`-suffixed sentinel keeps the operator after it

`0ne`/`0ie`/`-0ie` glued to a following sign or digit used to mis-lex: the type
suffix `e` was read as an exponent introducer, so `0ne+5` parsed as `0n` raised
to `e+5` and the `+` vanished. A NaN or infinity has no exponent, so that `e` can
only be the suffix:

```
  0ne+5.0e                 / v4: value error   v5: 0ne   (0ne + 5.0e)
  0ne-3                    / v4: 0n (an f64!)  v5: 0ne
```

The mirror case is fixed too (`5.0e+0ne` now lexes as `5.0e + 0ne`). Multi-digit
exponents are untouched (`5.0e+10n` stays `5e10` then `n`), and the one genuinely
ambiguous form still needs a space — `1.0e+2` is `100.0`, `1.0e + 2` is `3.0e`.

### Verbs, adverbs, and indexing



<a id="float-drop"></a>

#### `_` with a float rounds to a multiple

`f _ x` rounds `x` to a multiple of `f` — down when `f` is positive, up when
negative. The **atom** cases used to ignore `f` and round to the nearest whole
number, disagreeing with their own one-element vector:

```
  2.0_7.3                  / v4: 7.0       v5: 6.0
  -2.0_7.3                 / v4: 7.0       v5: 8.0
  0.3_-1.0                 / v4: -1.0      v5: -1.2
  2.0_,7.3                 / v4: ,6.0      v5: ,6.0   (the vector was right)
```

Two further atom faults are fixed too: `0.5_,0i` no longer hangs, and
`0.001_,1000000.0` is O(1), not a billion steps. `f _ x` is now documented in
[ref.md](ref.md).

---



<a id="nul"></a>

#### `nul` is the identity vector

`nul i` is `i` because indexing the identity vector at `i` yields `i` — not
because `nul` passes its argument through. v4 treated `nul x` as the identity
for *any* `x` and let any atom accept a `nul` index; neither is right.

```
  nul 1 2 3                / v4: 1 2 3     v5: 1 2 3     integer index
  nul `b                   / v4: `b        v5: nul       a symbol index misses
  nul "b"                  / v4: "b"       v5: type error
  5 nul                    / v4: 5         v5: rank error
```

The rule in full:

- an **integer** index (atom or vector) returns itself;
- a **symbol** index misses, giving `nul`;
- an **empty** index gives `()`, and so does `nul nul`;
- a char, float, dict or lambda is **not an index**: `type` error;
- a **non-**`nul` **atom** cannot be indexed by anything: `rank` error.

The other side `x nul` (the elided index, "all of `x`") is unchanged, and a path
applies one level at a time, so `nul . (i;j)` is `i[j]`, which ranks out (v4 gave
`1 2`). An **undefined symbol handle** still resolves to `nul`, so `` `nosuch 1 `` is
`1` — a bug in the script, not in gk.

---



<a id="derived-arg"></a>

#### an int left of a derived verb is its argument

`n f/x` and `n f\x` iterate (do `n` times / while) **only when** `f` **is a
monad** — a forced-monad lambda, a monadic builtin, or a one-slot projection. A
dyad-capable verb takes the left value as its **left argument**, as everywhere
else — and every derived verb (`(+\)`, `+\\`, a train like `(-%)`) is
dyad-capable:

```
  2(+\)\1 1                / v4: (1 1;1 2;1 3)     v5: 3 3
  3+\\1 1                  / v4: (1 1;1 2;1 3;1 4) v5: 4 4
  2 4+\\1 1                / (3 3;5 5)  unchanged -- and now the atom agrees
```

To iterate instead, spell the operator as a monad (see [digraphs.md](digraphs.md)):
a lambda (`2{+\x}\1 1` do-scans), a monadic builtin (`2 sqr/1.1`), or a
while-predicate (`{x<100}sqr/2`) — these all still iterate, unchanged. The one new
rule is that the verb's valence decides: the left value is a dyad's argument, never
a loop count.

---



<a id="sm"></a>

#### `sm` string match: `*` is zero-or-more

Three fixes to the glob matcher, one shared with `ss`. `*` matched **one** or
more, so `"ab"` failed against `"a*b"`; it is now zero-or-more.
`sm` also lacked the `[p-q]` ranges `ss`
had, and in both a failed class kept scanning, so a later class could mask it:

```
  sm["ab";"a*b"]           / v4: 0    v5: 1    * matches the empty gap
  sm["acc";"a[b-d]c"]      / v4: 0    v5: 1    [p-q] ranges, as documented
  sm["xd";"[ab][cd]"]      / v4: 1    v5: 0    failed class no longer masked
  ss["xd";"[ab][cd]"]      / v4: ,0   v5: !0   same masking bug in ss
```

Unterminated `[` still matches itself literally.

---



<a id="return"></a>

#### `:x` (return) must end its statement

A verb still pending when a return fires was silently discarded — the statement
quietly evaluated to `x` and the verb never ran:

```
  - : 5                    / v4: 5        v5: type error
  -':1 3 6                 / v4: 1 3 6    v5: type error
```

These spellings are k3 `':`/digraph leftovers (in k3 `-':1 3 6` is each-pair);
gk neither computed that nor errored, returning the right argument untouched.
Now it errors. Real returns are unaffected: `:x` as a whole statement, at top
level, or in a `$[c;:v;...]` branch works as before.

---



<a id="lambda-proj"></a>

#### a lambda projection is a noun

A lambda does not compose with a verb on its left (`,{x+y}` is a one-element
list, `-{x+y}` a type error), but a *projection* of a lambda formed a verb train,
inconsistently. Now a projection of a lambda is a noun exactly like its lambda:

```
  4:,{x+y}[1]              / v4: 7 (a train)   v5: 0 (a one-element list)
  -{x+y}[1]                / v4: applied        v5: type error, like -{x+y}
```

Projections and trains of **primitive verbs and builtins** compose as before
(`"."in'`, fixed dyads, verb chains). If you relied on a verb train over a
lambda projection, apply explicitly: `,f[1] x` → `,(f[1]x)`.

---



<a id="shift-rot"></a>

#### `shift`/`rot` promote to `i64` like every dyad

Every numeric dyad — arithmetic, `and`/`or`/`xor`, `div`, `gcd`/`lcm` — yields
i64 when *either* operand is i64. `shift`/`rot` alone took their width from the
left (value) operand, so an i64 shift *count* was narrowed and masked to 32 bits.
They now follow the same rule (value widening is sentinel-aware, so
`0N shift 3j` equals `0Nj shift 3`):

```
  1 shift 40j              / v4: 256   v5: 1099511627776j   (== 1j shift 40)
  1 shift 40               / 256       -- both i32: unchanged (count taken mod 32)
```

<a id="at-struct"></a>

#### `at` indexes structured values

`a at x` — index, but yield a null for an out-of-range position rather than an
`index` error — now works on lists, dictionaries, and symbol handles exactly as
`@` does. It used to `rank`-error on anything but a flat vector, and on a list
indexed *into* the left argument instead of selecting from it:

```
  (1 2;3 4)at 1            / v4: 2 4 (a column!)   v5: 3 4   (item 1)
  (1;"a")at 0 5            / v4: rank error        v5: (1;)  (nul fills OOB)
  d:.+(`a`b;1 2); d at `z  / v4: rank error        v5: nul   (missing key)
```

A symbol handle derefs and indexes the named variable; an out-of-range integer
index still yields the type's null.

### Scoping and namespaces



<a id="global-ns"></a>

#### a global assign writes the defining namespace

`::` (and the compound forms `+:`, `,:`, and indexed ``d[`k]::``) assign to a *global*. Which global was decided partly by the **caller**: a function defined under` \d foo`and called from anywhere else could not update`foo`'s state.

```
  \d foo
  c:10
  bump:{c+:1;c}
  \d .k
  foo.bump[]               / v4: 11    v5: 11
  foo.bump[]               / v4: 11    v5: 12
  foo.bump[]               / v4: 11    v5: 13
  foo.c                    / v4: 10    v5: 13
```

In v4 the write was **silently discarded** — the store resolved `foo`'s
namespace as an ordinary lambda parent frame and wrote a local that vanished on
return, so the counter never advanced and nothing was raised.

In v5 a name assigned with `::` inside a function belongs to **the namespace the
function was defined in**, whichever it is called from — matching the read side.
So a name existing **nowhere** is created in the function's own
namespace (`{zz::7}` under `\d foo` creates `foo.zz`, not root `zz`), and one
existing **only in the caller's** namespace is still not touched. Unchanged: a
local shadows the global (`{c:5;c::6;c}`), closures mutate their captured frame,
and assigning into a namespace the function is *not* defined in needs the
qualified name (`foo.c::1`). This is what lets a stateful `\d`-namespaced package
(the mechanism [ref.md](ref.md#load-path-gkpath) recommends for `2:` shims) keep
state.

---



<a id="proj-value"></a>

#### a projected argument is a value

A held argument is an independent value, never a reference. gk already enforced
this for the namespace tree (`d.b:.k` stores a snapshot), but a projection
slipped past it: `@[;].k` held a *live* reference to `.k`, and storing that
projection back into the tree closed a reference ring (`.k → d → p → .k`) that
refcounting can never reclaim — the one way gk could be made to leak. A shared
dictionary argument is now copied at every projection-formation site, so the ring
cannot be built:

```
  a:1
  p:@[;].k
  a:2
  p`a                      / v4: 2 (live tree)   v5: 1 (snapshot at formation)
```

For ordinary dictionaries nothing observable changes — a write to a shared
dictionary already copied it (`e.v:8` after `w:@[;]e` left `w` at 7 in both), the
copy just happens eagerly now. To operate on the live tree, name it: ``@[`d;;:;]``
amends through the symbol handle, a reference by design. The closure exit gate's
ring walk also learned to cut cycles, kept as defense in depth.

### Commands and reserved words



<a id="pezc"></a>

#### `\p` `\e` `\zc` reject a malformed argument

Each takes a bare digit run, or nothing to query. A malformed argument used to be
left on the line, reducing against the `nul` the lexer pushes for the missing
argument — so the command never ran and the statement echoed as `nul <argument>`:

```
  \p "x"                   / v4: "x"       v5: parse error
  \zc `a                   / v4: `a        v5: parse error
```

In v4 none of these changed the setting they appeared to accept. `\m` `\d`
already rejected bad arguments; now these do too, including junk after the digits
(`\p 5x`).

---



<a id="dot-r"></a>

#### `.r` lists the reserved words

Every reserved name now lives in a read-only top-level namespace `.r`, beside
`.k` and `.z` — one key per reserved word, each value the builtin itself:

```
  !.r                      / list every reserved word
`nul `draw `dot `vs `sv `atan2 ...
  .r.sin 0                 / the values are the builtins, and apply
0.0
  .r.dv[1 2 3;2]           / including the predefined fns (dv, gtime, ssr, ...)
1 3
```

### Binary compatibility



<a id="ffi-abi"></a>

#### the `2:` FFI ABI counts vectors in 64 bits

A `2:`-linked shared object builds gk values through the ABI in `gk.h`. Its
*read* side was already 64-bit (`gk_n` returns `uint64_t`), but every
*constructor* took a 32-bit length, predating big-vector support — so a shim
could not build a vector past `2³¹` elements. The count parameters are now
`int64_t`:

```
  gk_mkiv gk_mkfv gk_mkjv gk_mkev gk_mkcv gk_mksv gk_mkkv   / (int64_t n)
  gk_mkstrn(const char *s, int64_t n)
  gk_dict(const char **keys, const K *vals, int64_t n)
```

**This is the one non-upward-compatible change in v5.** The calling convention
widens, so a `.so`/`.dll` compiled against an older `gk.h` must be
**recompiled** — no source change needed (a normal `int` count still passes),
only a rebuild.

The same pass made the wrappers refuse a caller's slip instead of crashing: a
dict reader handed a non-dict now returns a `type` error (was a segfault), and a
negative constructor length returns `wsfull` (was a multi-exabyte allocation and
process exit). These are robustness fixes for `.so` authors, not security fixes —
loading a `.so` is already arbitrary code execution.

## Part II — Performance improvements

No semantic change; output is byte-identical.


|                               | v4       | v5      |      |
| ----------------------------- | -------- | ------- | ---- |
| `&b` where, dense mask, 1e7   | 42.7 ms  | 10.3 ms | 4.1x |
| `&x>500000` fused, dense      | 52.1 ms  | 8.9 ms  | 5.9x |
| `&x>990000` fused, sparse     | 19.5 ms  | 4.9 ms  | 4.0x |
| `f>0.5` float compare, 1e7    | 60.5 ms  | 14.1 ms | 4.3x |
| `f~h` match, equal 1e7 floats | 30.6 ms  | 15.0 ms | 2.0x |
| `\|/f` max, 1e7               | 17.1 ms  | 12.0 ms | 1.4x |
| `?m` distinct, 2e6            | 107.6 ms | 62.9 ms | 1.7x |


<a id="perf-where"></a>

#### branchless `where`

`where` expanded its counts with a data-dependent branch, mispredicting once per
element on a random mask. It now proves the mask is 0/1 in the pass that already
sums it, then compacts branchlessly — 4.1× on a dense mask.

---



<a id="perf-cmp"></a>

#### one float comparator

`cmpfft`, the float comparator, was an `isnan`/`isinf` ladder that couldn't
vectorise; it now has a branchless closed form. Its tolerant twin `cmpff` became
identical to it when tolerance was removed in v4, so the two collapsed into one —
which is why `min`/`max`, `distinct`, `group`, and `match` all moved (2–4×).

---



<a id="perf-fuse"></a>

#### fused `&a<x` / `&a>x` / `&a=x`

The 0/1 mask is never built: the parser routes the comparison straight into the
index-producing kernel. `w:&x>c` on 1e7 elements runs ~5× faster, and its peak
memory falls from 84 MB to 46 MB.

---



<a id="perf-intatom"></a>

#### int-atom fast path

`+ - * & | < > = ~` on two plain int atoms now compute inline — a wrapping op, a
min/max, a signed compare, or a bit-equality — skipping the dispatch chain and the
primitive prologue.

---



<a id="perf-amend"></a>

#### amend copy-on-write

``@[`a;i;:;v]`` and the deep-amend walkers mutate the target in place when its
refcount shows it is uniquely held, instead of copying the whole structure on
every amend — about **4.3×** on an amend-heavy benchmark.

---



<a id="dict-o1"></a>

#### dict lookup and amend are O(1)

Dictionary lookup was a linear scan of the key vector — O(n) per lookup,
O(n²) to build or query a big map — and a by-name dict amend additionally
deep-copied the whole dict on writeback, so a dict was unusable as a large
memo table.  Both are fixed:

- at 32 keys and up, a dict carries a hash table over its interned key
pointers (a 4th payload slot, rebuilt lazily when stale), so ``d[`k]``, ``d[`k]:v`` and ``@[`d;`k;:;v]`` are O(1); smaller dicts (lambda frames,
most namespaces) keep the linear scan and never build one;
- ``@[`d;`k;:;v]`` amends the stored dict in place and assigns the same
object back — scope_set now recognizes that store and skips the
whole-dict copy (no new alias is created), as it always did for vectors.

100k-key dict, before → after: full lookup sweep 1.18s → <0.01s; building
50k keys by amend 6.4s → <0.01s (was quadratic, now linear).

`kreserved()` — consulted on every assignment — moved to the same trick: a
small hash set over the interned reserved names replaces the ~100-compare
chain, which was ~16% of a global-assign-heavy workload.

Nothing user-visible changes otherwise: insertion order, print/unmake/flip
shapes, `bd`/`db` wire format (the table is never shipped), and
duplicate-key first-wins lookup (``.+(`a`b`c`c;1 2 3 4)``) are all exactly as
before.

<a id="part3"></a>

## Part III — Bug fixes

### Forms that used to error, crash, or hang



<a id="closure-kill"></a>

#### creating closures no longer kills the interpreter

Every closure snapshotted the frame it captured, and `scope_cp` walked up to the
root, so each one deep-copied **the entire global scope and the ktree** — a copy
refcounting could never free (its inner lambdas pointed back into it). The
workaround registered each copy in the fixed-1000 table meant for *namespace*
teardown, pinning it forever; when the table filled, gk printed
`error: scope_new() i==SM` and called `exit(1)` — not a trappable `k` error:

```
  u:{c:x;{c*x}}
  do[400;u 3]              / v4: error: scope_new() i==SM, process gone
                           / v5: fine (500000 is fine)
```

A snapshot now copies only the **lambda frames** the closure captured; namespace
scopes are shared (lookup refreshes them from the ktree anyway, so the copies
were never read). Closure creation is also **19× faster** (45.8µs → 2.4µs). The
table now holds only namespaces and grew from 1000 to 16384; should it ever fill,
that is a trappable `limit` **error**, not `exit(1)`.

---



<a id="closure-wire"></a>

#### a closure survives serialization

`bd` did not carry a lambda's captured environment, so `db` handed back a
function whose captured names were **gone** — a silently broken value that failed
the moment you applied it (and `bd` of a closure was byte-identical to `bd` of the
bare lambda). IPC serializes, so this hit every closure sent to a peer:

```
  u:{c:x;{c*x}}
  v:u 3
  (db bd v)4               / v4: value error (c)   v5: 12
```

What travels is the **captured environment** — the bindings of the enclosing
lambda frames, flattened with inner names shadowing outer; nested frames, a
captured function, and a captured closure all come across. **Globals do not
travel**: the walk stops at the first namespace scope, so free globals still
resolve against the *receiver*.

```
  g:100
  u:{c:x;{c+g+x}}          / c is captured; g is not
  (db bd u 3)1             / 104 here -- but on a peer without g, a value error
```

Each message carries its own snapshot (no shared mutable state across a wire). A
plain lambda captures nothing, so its bytes are **unchanged**.

---



<a id="recursion"></a>

#### local and mutual recursion work

A lambda captured in a closure could not see the frame it lives in, so three
shapes value-errored — a sibling reached through an inner closure, a **local
recursive function**, and **mutually recursive locals**:

```
  {c:5;f:{c*x};{f x}}[]3          / v4: value error   v5: 15
  {f:{$[x<1;0;x+f x-1]};{f x}}[]4 / v4: value error   v5: 10
  {f:{x*2};g:{f x};{g x}}[]5      / v4: value error   v5: 10
```

`f` could be *called* while its frame lived, but once the frame was captured only
the *returned* value was re-parented to the snapshot; every other lambda inside
still pointed at the live frame the return then reset. Now the snapshot's own
lambdas are re-parented too, and a closure escapes in **any returned shape** —
bare, under a projection/adverb (`f'`), in a verb train (`,(f 1)`), in a
projection's held arguments, in a dictionary, or nested in a returned list.
Frames that define no local lambda (almost all code) skip the analysis, so
nothing gets slower; it all holds across `bd`/`db` and IPC.

Each re-parented lambda closes a reference ring (snapshot → lambda → snapshot,
~10KB) that refcounting alone can't free, so a targeted **cycle collector** parks
each snapshot and frees the rings nothing outside can reach; the test is exact,
so a closure still reachable holds its ring alive, and 100 000 discarded closures
cost no more than 10.

---



<a id="nested-lambda"></a>

#### a nested lambda after a name keeps the parameters

The scan that discovers a lambda's implicit `x`/`y`/`z` lost track of its brace
depth when a nested lambda directly followed an **identifier**, never leaving the
nested-lambda state — so every `x`/`y`/`z` *after* that inner lambda was invisible.
The parameters were never bound (a reference reached past the function for a
missing global) and valence was under-counted:

```
  g:{y}
  {g{1};x}4                / v4: value error   v5: 4
  {g{1};x+y+z}[1;2;3]      / v4: value error   v5: 6
  val{g{1};x+y}            / v4: 1             v5: 2
```

It was whitespace-sensitive — a single space, parens, or brackets around the
inner lambda ended the identifier and everything worked (`{g {1};x}4` is `4`).
Formal parameters suppress the implicit scan entirely, so `{[a;b]g{1};a+b}` was
never affected.

---



<a id="do-while"></a>

#### a monadic builtin is a primitive do/while controller

`n f/x` and `b f/x` read their left argument to pick the mode: a non-negative
int is `do`, a monadic predicate is `while`. Every way of naming that predicate
worked except the shortest — a **bare builtin** parsed as the outer monad, so the
derived verb reduced as monadic `f\x` (converge), and a non-converging `f` looped
forever:

```
  prime{x+1}\4             / v4: hangs, silently   v5: ,4
  {x+1}\[prime;4]          / ,4 -- the bracket spelling always worked
  c:prime; c{x+1}\4        / ,4 -- the same builtin via a name, always worked
```

Only a builtin **monad** is a controller; a dyad-capable verb (primitive,
dyadic builtin, derived verb) takes its left as an argument, not a loop count
(`#{z;x+y}\[0;1 2 3;nul]` is `4`, the count of the scan). A bare verb is still
not a noun, so `sqr@1 2 3` is `sqr(@1 2 3)` — unchanged.

---



<a id="named-verb"></a>

#### a named builtin is a verb everywhere

Assigning a builtin to a name kept bracket application but lost adverbs and
infix use. The value a name resolves to now dispatches through the same adverb
and dyadic-juxtaposition machinery as the bare name, including do/while forms
for monadic builtins:

```
  f:mul; f/1 2 3           / v4: type error   v5: 6
  g:in; 2 g 1 2 3          / v4: type error   v5: 1
  h:sqr; 2 h\1.1           / v4: type error   v5: 1.1 1.21 1.4641
```

---



<a id="div-zero"></a>

#### `div` by zero is infinity

`%` yields infinity on a zero divisor and `!` yields a null, but `div` — the
third of gk's integer-division family — raised `domain`. It now agrees with `%`:

```
  5 div 0                  / v4: domain error   v5: 0I
  5j div 0                 / v4: domain error   v5: 0Ij
  -5 div 0                 / -0I    -- sign follows the numerator
  0 div 0                  / 0N     -- zero-over-zero is null, as 0%0
```

The result width follows the usual promotion (an `i64` operand gives
`0Ij`/`0Nj`). `INT_MIN div -1` still raises `range` — a real overflow, not a zero
divisor.

---



<a id="byref-ns"></a>

#### a by-reference amend writes the function's namespace

The rule above — a global reference inside a function belongs to the namespace it
was **defined** in — applies to the by-reference amend family too. The *read*
side already worked (a `` `v `` inside a `\d ns` function found `ns.v`), but the amend
family resolved its symbol against the **caller's** namespace, so a function could
not amend its own state:

```
  \d .k.ns
  v:1 2 3
  w:{@[`v;0;:;9];v}
  \d .k
  ns.w[]                   / v4: rank error   v5: 9 2 3
```

Called from root it looked for a `v` root didn't have (amending `nul` at an index
is `rank`). All four amend forms are affected (``@[`v;i;:;y]``, ``.[`v;i;:;y]``, an
amending verb, a dict by reference). A **watch** on such a variable now fires for
those writes too; a local of the watched name still never fires.

<a id="edge-case"></a>

### Edge-case crashes, leaks, and wrong answers

- `(5+)1 2 3` silently dropped its argument and returned `5+` — a
parenthesized left-seeded partial dyad never became a closed value, while
the same value bound to a name applied fine.  `(2 3+)10 20`, `(5+/)1 2 3`,
`(1+)2` all affected.
- ``{`x`y}`` and `{a.y}` grew phantom parameters.  A symbol list at the
start of a lambda body, or a dotted global whose post-dot component was
literally `x`/`y`/`z`, was scanned as parameter names — the lambda became
valence 2 and returned a projection instead of its value.
- Closures hiding inside a seeded fold/scan value never converted:
`{c:5;g:{x+c};3 g/}` returned a value that failed with a stale-frame value
error.  The 0xd7 seeded-over subtype was missing from every closure
walker; it now converts, collects, and serializes like the rest.
- i64/f32 vectors broke multi-char adverb chains (`+/'1 2j` errored;
`1 2j+/'(1 2;3 4)` silently DROPPED the left argument) and were silently
dropped when amended into a dict (``@[d;`a`b;:;10 20j]`` returned d
unchanged, no error).  Both were missing `-8`/`-9` type arms; the amend
switches now error on any future unhandled type instead of falling
through.
- A dict argument confused multi-arg fold/scan conformance:
`{[a;b;c]c}/[0;d;10 20 30]` valence-errored because the dict's internal
slot count seeded the length check.
- A deep scatter re-broadcast through symbol levels:
``.[d;(`a`b;`x;`p);:;10 20]`` set BOTH leaves to `10 20` instead of 10 and
20 — one `y` where `y_` was meant.
- An empty path element in 3-arg amend-at-depth spuriously
index-errored where the 4-arg form correctly no-ops.
- An adverbed builtin monad died as a value: `sqrt/16.0` worked but
`g:sqrt/; g 16.0` and `(sin')1 2 3` type-errored.
- An adverbed projection of a `2:`-linked function was double-freed —
after a few `add[3;]'4` calls, any call segfaulted.  It now applies through
the same adverb route as builtin dyads (`add[3;]'4` → 7).
- `_[n;f;x]` on a vector too short for one pair now yields `()` for every
stride — stride 1 already did (by a wraparound accident the suite
depended on via `ssr`), stride 2+ spuriously valence-errored.
- `\V` corrupted the length of a >2³¹-element vector — the display
clamp saved and restored the count through an i32.
- `3{2*x}'/1 2` valence-errored while `3{2*x}/1 2` gave `8 16`: do-n and
do-scan now accept any monadic-only `f` — including a val-1 lambda — not
just the subtypes that happened to be listed.
- `_[n;f;x]` raises `length`, not `valence`, on a ragged tail, as the
spec always said.
- `draw[0;1.0e]` type-errored — an f32 range was the one hole in
the roll/deal type grid (`0?1.0e` already worked).
- `in . ,1` type-errored where `.[in;,1]` gave `in[1]`.  A builtin name
lexes as a verb, so the `.` had no left operand and bound monadically:
the expression parsed as `in(. ,1)` — the *value* of an int vector.  A
builtin dyad has a known valence of 2, so composing it with a monadic
`.` could only ever project; the useful reading is dot-apply, and
`in . ,1` now means exactly `.[in;,1]`.  An ambivalent verb — whose
effective valence is decided by context — keeps its real composition:
`4:."1 2 3"` is still `4:` of the *value* of that string, `f:4:.` is
still a valence-2 value, and `5:.()` / ``bd .+(`a`b;1 2)`` are unchanged.
- Three error-path leaks in amend, a latent borrowed-element corruption in
fold/scan cleanup, a latent heap overflow in slide's unused adverb path,
and a latent `exit(1)` reachable through khash on a parser-internal
subtype.
- `sv` truncated its shared right argument in place. `c:10 20 30; (2 3 4)sv c` left `c` as `10 20` — the base-decode borrowed the vector,
shortened it to align the digit count, and never restored it.
- `hb bh"abc"` dropped a byte. An odd-length hex string left its last
byte uninitialized. Two characters per byte is the contract, so an
odd length is now a `length` error. (Shipped in prod v4.)
- Sort ordered ragged nested lists by length, not element-wise.
`<((1 2;9);(1 2;3;4))` graded by count where the shorter list should
compare by its first differing element — grade, sort, `bin`, all of it.
- `+1 2 3j` was a type error. Flip's pass-through arm was missing the
i64/f32 types; so was the char-vector min/max against a general list
(`"ab"&(,"a";,"z")` length-errored).
- `%/1 2 3.0e` silently widened to f64 — divide's fold/scan lost the
f32 tag on the way out (a golden had enshrined the wrong type).
- `lu` of a non-finite matrix returned `(L;U;P)`, not `(+P;L;U)` —
the early-exit tuple was assembled in the wrong order, and `ldu`
inherited the corruption.
- `lcm` of two i64s that overflow now saturates to `0Ij` like the i32
arm always did, instead of wrapping to a garbage product.
- A deserialized symbol could read past the buffer. The `db` guard
against an unterminated name was dead code (`strnlen` made the check
unfalsifiable) and the scalar path used an unbounded `strlen` — an
untrusted/IPC blob could read out of bounds.
- `inv` and `lsq` type-errored on a matrix with mixed int/float rows.
Every other entry point (`lu`/`qr`/`svd`/`mul`/`det`/`rref`) accepted
them; `lsq` transposes its design matrix first, and mixed rows flip to
general-list columns. They now widen to f64 like everything else.
- `%!0` lost its type. Reciprocal of an empty int or float vector
returned the untyped `()` instead of `0#0.0` (the i64/f32 arms were
already right).
- Shape invented dimensions for ragged lists — three ways. When an
atom ended a dimension, children already enqueued from earlier siblings
kept the breadth-first walk alive one level deeper (`^((,0;,1);-17)`
gave `2 1`, not `,2`). An *empty* child arriving first never recorded
its count, so a nonempty sibling didn't conflict (`^((^-18);,16)` gave
`2 1`). And a plain-vector sibling next to a deeper list dropped out of
the walk silently instead of ending it, growing a phantom dimension
(`^((,16;,(-19,!3)))` gave `2 1 4`, not `2 1`). A level's count now
starts unset, and a deeper level exists only if *every* node
contributed children.
- `_ -0i` was `0N`, not `-0I`. The floor verb clamped +infinity to
`0I` but negative infinity — and any float below the int64 range — to
the int *null*, one below `-0I`. Now symmetric on every arm (f64 and
f32, atom and vector), and the i64 path clamps to `-0Ij` rather than
`0Nj`. (`0n` still floors to `0N`, and the float-in/float-out `floor`
builtin is untouched.)
- `factor` of a large i64 could take an hour. The 64-bit path was
pure trial division — a ~2⁶³ prime (or a semiprime of two ~2³¹ primes,
`factor 2147483647*2147483647j`) needs ~1.5 billion iterations. The
small factors still come from trial division; whatever remains is now
split by the deterministic Miller-Rabin that `prime` always used plus
Pollard's rho, so any 64-bit input factors in milliseconds (verified
against an independent oracle on 534 randomized cases: exact product,
every factor prime, ascending order). Also: `factor 0N` read the int null as 2³¹
and returned thirty-one 2s; both nulls now yield the empty, like 0
and 1.
- `prime` on an int-range vector paid a 64-step loop per multiply.
The overflow-safe modular multiply always used shift-and-add, even
when the modulus fits 32 bits and one machine multiply suffices —
`prime 100000#0I` took 18 seconds. Miller-Rabin and rho now run over Montgomery
products (four machine multiplies per step, plain C), which also cut
the hard 63-bit cases ~50×. `factor`/`prime` test primality *before*
trial division (a large prime paid 23k wasted divisions), vectors of
repeated values factor once per distinct value, and the per-element
temp atom the vector path leaked (24 bytes each) is freed.
- A typed-empty `.` path on data returned the first element. For
data, `d . i` is `d@/i` — a fold over the indices — so an empty path
of *any* type is `d` itself (e.g. `10 . ()`).
gk converted `!0`/`0#0.0`/`""`/`` 0#` `` to that type's prototype atom and indexed: `"ab" . !0` was `"a"`, `1 2 . !0` was `1`, silently; a plain numeric atom with `()` rank-errored; and `!0j` already did the right thing, disagreeing with `!0`. Empty paths on data are now the identity across every type, for vectors, lists, dicts, atoms, and name handles. Function application keeps the prototype rule: a typed empty as the argument list still calls with that type's prototype argument (`{1,x} . 0#0`→`1 0`), and the i64/f32 arms that predated those types now exist too (`f . !0j`→`f[0j]`; it used to pass the empty vector itself). Brackets stay strict: `5[]` and `5[0]` are rank errors in gk.
- `deal` returned the identity permutation after ~32 calls. The deck
shuffle behind `n?-m` / `draw[n;-m]` ran a broken LCG — the multiplier
was accidentally even, so its state reached zero after 32 calls and
stayed there, and every deal from then on returned `0 1 2 … n-1`
unshuffled, process-wide. It now uses a proper xorshift generator (and
is reseeded per forked child, so IPC workers get distinct deals). `?`
*roll* (positive range) was never affected.
- `draw[2 3;1.0e]` — a shaped draw from an f32 range — was a type
error though `draw[6;1.0e]` and `0?1.0e` worked. The vector-count arm
was missing the f32 case.
- `md5`/`sha1`/`sha2` now recurse into nested lists like every other
monadic builtin (`md5 ,,"abc"` was a type error; it now digests
element-wise through any depth). A non-string leaf still type-errors.
- A one-item fold no longer retypes its item. `f/y` on a one-item
list is `*y` and f is never applied — but the float-forcing folds
converted the untouched item (`%/,-19` was `-19.0`; it is `-19`).
- `empty#empty` yields the prototype of the right argument. Reshape
by empty dims always returned the first element of a *nonempty* right
argument; an empty right argument gave nul for the numeric types where
it should give the type's prototype atom. Now: `()#!0` → `0`,
`0.0`, `0j`, `0.0e`, `" "`, `` ` `` per type; `()#()` stays nul.
- An i64 index vector made scatter-assign quadratic on retype.
`a[b-0j]:b-1.0` amended once *per index*, re-walking the base each
call whenever the value type forced a base retype — 777k indices
never finished. A narrow i64 index vector now
converts to int once and takes the same vectorized path as `a[b]:v`;
results are byte-identical, and >2³¹ bases keep the per-element path.
- `=` and `?` were quadratic on floats, strided ints/longs, and
strings. The group/unique table hash kept only the *low* bits of
`value*2654435761`, which depend only on the value's low bits — and
whole data classes have constant low bits: every integer-valued double
(zero low mantissa — `=5.0-!100000` put all 100k elements in one probe
chain), stride-2^k ints and longs, and, through the same combine in
`khash`, lists of short strings (`=$!100000` — grouping a formatted
column). A murmur-style
finalizer now feeds the table index (strings hash via fnv1a, as
symbols always did) and all of them run in ~100–600ms at 10× the
size. Grouping semantics are unchanged — ±0.0 still share a group,
`?` still keeps the first-seen zero's sign, general lists still group
type-strictly.
- On exec failure the spawned child of `6:` kept *running the
interpreter* — two processes sharing one stdin; `execvp` now `_exit`s.
Plus two IPC error paths: a >4GB client send truncated its length to
u32, and a malformed sync request was answered with a raw (non-`bd`)
error string the peer couldn't decode — the exact hang that reply
exists to prevent.
- `draw[n;m]` rejected an `i64` range. The primitive accepted it
(`20?100j`), but the builtin's type guard did not: `draw[20;100j]` was a
`type` error, as was a shaped `draw[2 3;100j]`. Ordinary code hit this
through `#`, which returns an i64 on a big-vector build:
`draw[20;#v]` could not be written at all.
- `bin`/`binl` never moved past a `0n` in a sorted float haystack. C's
`<` is false on NaN, but gk's own grade and `<` sort nulls below everything:
`0n 1 2.0 bin 1.0` returned 0 instead of 1.
- `x:mul/1 2 3` could not parse. The assignment target was consumed as an
each-right seed, so assigning any adverbed named builtin failed — plain
(`value`/`valence` error) or compound (`r,:9~lcm/1+!20`, `parse` error).
- A zero-size allocation raised `wsfull` and exited in every build that does
not use the buddy allocator — which is all of the MSVC build. Any filter that
matched nothing (`&1 2 3>9`) killed the interpreter.
- `?` distinct dropped the sign of a leading `-0.0`. Zeros bypass the probe
table (`0.0` is its empty marker) and the bypass emitted a literal `0`.
- `-0` in a float vector literal lexed to `+0.0`. The literal's int tokens
are promoted only when a float token appears, and by then `-0` had become the
integer zero. `1%*-0 1.0` was `0i`; it is `-0i`.
- `-0j` promoted to `-0.0`. A `j` suffix types the token an i64,
and integers have no signed zero. (The literal is now rejected outright — see above.)
- A script that failed to load left you in its namespace. `load`'s error
exits — a parse error, an eval error, a bare `\` abort — skipped the
namespace restore that a successful load performs, so a `\l` that died
after a `\d` stranded the *caller* in the dead script's namespace (and
leaked the two scope references the restore releases).
- `=` (group) hung forever on an int vector holding a sentinel next to a
normal value. `=0I,1`, `=0N,1`, `=-0I,1` never returned: the hash table
was sized from a min/max scan that skips sentinels, so there were more
distinct values than slots and the probe never found a free one. Ordinary
code hit it as `=72337203685477,1` — a bare over-2³¹ literal clamps to
`0I`. `?` (distinct) already carried the needed headroom; group and its
big-vector twin now match.
- A parse error in an unclosed multi-line statement could print ~2⁶⁴ spaces.
The open-error caret clamped the wrong variable when the column went
negative, so the space loop before the `^` ran on a sign-extended count.
- A runaway-recursion script took effectively forever to die at EOF. The
first error subconsole hitting end-of-input sets the exit flag, but five
subconsole gates didn't check it, so every level of a deep unwind opened
another subconsole and printed an ever-longer prompt to unbuffered stderr —
quadratic one-byte writes. All gates now honor the exit flag.
- A bare `\` abort inside a lambda whose frame defines a lambda crashed the
interpreter. The closure exit gate walks every return value from a
flagged frame, but an aborted body hands back the exit sentinel — not a
value — and the walk dereferenced it. Error returns were exposed the same
way. The gate now checks for both first, as the pre-flag shape checks did
implicitly.
- A cyclic value graph crashed the closure exit gate's walk. A wrapped
reference to a namespace dict stored back into the tree (`d.b:@[;].k` —
the write path's guard only copies a bare shared dict) closes a reference
ring the walk had no defense against: the capture probe's depth guard
reported "captures" for a return with no capture at all, and the
conversion walk then revisited the ring's nodes until its own guard
fired, whereupon the error unwind freed each node once per visit —
use-after-free. Both walks now stop at any node already on their own
path, so cyclic returns walk cleanly and convert what they can reach.
The ring itself is no longer constructible — see
"a projected argument is a value" above — so the cut is defense in depth.
- `sm` went exponential on runs of wildcards. The glob matcher recursed
over every subject position per `*`, so a pattern like `"a****…**x"`
against a short subject never returned. Rewritten as the standard
iterative match that backtracks to the last star only — worst case
O(subject × pattern), per-token semantics unchanged (verified against
the old matcher on 2,500+ randomized cases).
- `db` (deserialize) could read past a truncated buffer. The remaining-
byte counter was decremented only through element *headers*, never the
fixed scalar and vector *payloads*. Because a nested list threads that one
counter across its siblings, a truncated or hostile blob (`db -2_bd x`, or
any short IPC frame) kept passing the length guards while the read pointer
ran off the end — a heap over-read, and an arbitrary one from crafted
input. Every case now decrements by exactly the bytes it consumes, and a
symbol vector cut off mid-element frees its partial result instead of
leaking it. `db` on untrusted data is the IPC receive path, so this is a
serious one.
- `gcd`/`lcm` trapped on the i64 minimum. `0Nj` reads as its magnitude
2⁶³, and negating `INT64_MIN` in a signed `i64` is undefined — at `-O3` it
trapped (SIGILL), and elsewhere returned a wrapped-negative result
(`gcd[0Nj;6j]` → `-2j`). The kernels now compute in `u64` and saturate an
out-of-range result to `0Ij`, matching the int path's `0I` clamp.
- A boxed `i64` atom applied with brackets leaked it. `5j[]` ranks out
(an atom is not indexable), but the rank-out path freed only a boxed `f64`,
not a boxed `i64`, so every `5j[…]` leaked the atom.
- A deep amend with an out-of-range `i64` index leaked the index. The
`index`-error exit of the `.[m;i;:;v]` engine (both the 3- and 4-argument
forms) dropped its boxed `i64` index atom on the floor.
- `timer` with an astronomical interval trapped. A finite but huge float
(`timer 9e95`) overflowed the `double`→`i64` cast that computes the next
tick — undefined, a SIGILL in practice. The conversion is now clamped to
~285 million years, effectively "never."
- `n f\x` (do-n scan) with `n` = `0Ij` crashed. The result list was sized
`1+n`; at `n` = `INT64_MAX` that overflowed to a negative count and the
allocation wrapped to ~2⁶⁴ bytes — a segfault in production. Now a clean
`limit` error.
- `sv` with an empty base vector crashed. `radixes sv digits` with an
empty `radixes` left `*\|a` empty, then a count decrement underflowed to
`SIZE_MAX` and the following reverse attempted a ~2⁶⁴-byte allocation
(silent death in production). An empty base has no places, so the decode is
now `0`, matching the i64 `sv` path.
- A watch whose trigger expression fails to parse leaked on every fire.
The lexer freed the previous cached error-line before overwriting it for one
of its two line buffers (`glinep`) but not the other (`gline0p`), so any
non-repl caller that parses and errors without reaching the repl's
display-and-free — a `watch`, a `.`-eval (`valuecb`), a lambda body (`fnd`)
— leaked the line text each time. A long-lived process watching a
frequently-assigned variable with a typo'd expression leaked steadily.
- Base conversion (`sv`/`vs`) and format-width (`$`) had signed-overflow
UB. The `sv` i64 Horner accumulator, the mixed-radix place products, and
the `double`→`i64` width cast in dyadic `$` all overflowed signed integers
on out-of-range input — undefined behavior, though
production's `-O3` wrapping and post-cast `wsfull` check masked it. All now
compute in `u64` / guard the cast, with byte-identical results.
- Bracket-applying a lambda to a variable holding a boxed `i64` leaked the
value on every call. `x:5j;g:{x};g[x]` left `x`'s value with a permanently
raised refcount — once per call, so a loop climbed it without bound. The
inline bracket-apply's arg-release loop hand-listed the heap-boxed types
(vectors, float atoms) and predated the `i64` type, whose boxed
atoms it skipped; it now asks `kh()`, the one canonical is-it-heap test.
Results were always correct — only memory grew, and only for `i64` (and
in principle any future boxed-atom) arguments.
- Appending to a `db`-roundtripped EMPTY dict corrupted the heap. The
wire fix that resets a dict's capacity to its key count on arrival left an
empty dict with capacity 0 — and `dset`'s grow step doubles, and 0×2 is 0,
so the "grown" key/value vectors were rebuilt zero-sized and the append
wrote past them (a segfault in production: ``d:db bd .(); d[`z]:7``). A zero
capacity now grows to the same 128-slot floor a fresh dict starts with.
- Assigning into a namespace whose tree node was destroyed leaked the
value. Every error exit of the scope writer frees the value it was
handed — except the one that fires when the namespace's backing node can't
be fetched from the tree (a `\d a` left active while ``.[`;…]`` rewrote the
root out from under it). Each assignment attempt in the orphaned namespace
then leaked the fully-computed right-hand side. The join/take/enumerate
"operand leak" family all bottomed out here.
- Composing past the 255-adverb cap leaked the composition. The
adverb-with-args eval branch retains the node's operand pair, but its
`length`-error exit (combined adverb string ≥ 256) released only half of
it, leaking the composed verb train — e.g. a lambda followed by 256 `'`s
and a train tail. The sibling error exits in the same branch already freed
both.
- `1:` (mmap file read) trusted the on-disk element count. The 24-byte
header of a `1:`-mapped file carries the vector's element count, and the
reader used it without validating it against the actual file size — and
`count * elemsize` could overflow. A crafted header claiming ~2⁶² ints made
`len = count*4` wrap to a small value, so `mmap` mapped a tiny region while
the returned vector's count was set to billions: any use read off the end
of the mapping — a segfault, and an out-of-bounds read of live process
memory (an info leak) from an untrusted file, before that. `1:` now checks
the count against the file size with a divide (no overflow) and errors
cleanly; a valid file still zero-copy maps. Both the POSIX and Windows map
paths are fixed.
- A hostile IPC header could kill the server (remote DoS). The receive
path preallocated the full message size declared in the wire header before
any body bytes arrived. `msglen` is untrusted, so a 12-byte v2 header
claiming a multi-terabyte message made the receiver `xrealloc` that size;
it failed → `wsfull` → `exit(1)`. One tiny frame from any peer killed a gk
IPC listener. The receiver now grows its body buffer incrementally as bytes
actually arrive — a peer that wants it to hold N bytes must send N bytes —
so an inflated header claim allocates nothing large. Large legitimate
messages still round-trip (the buffer doubles toward the real size).
- `group` (`=`) overflowed when a `-DFUZZING` `khash` budget crossed zero
mid-pass, so the count and fill passes hashed an equal value to different slots
and the fill wrote past a count-sized vector. The budget now resets per top-level
`khash` call — also fixing `in`, `distinct`, and the dict index. `t768`.
- `factor` hung on a thrashing repeat cache — `2` and `INT64_MIN+2` share the
cache's low-3-bit key, so a vector alternating them re-factored every element. A
Fibonacci hash caches both; `-DFUZZING` also budgets the unbounded
many-distinct case to a fast `'limit`. `t768`.
- A digit literal transmuted into infinity at exactly three magnitudes:
`2147483647 1 2 3.0` was `0i 1 2 3` while its neighbors `2147483646` and
`2147483648` kept their values. The lexer records each token's *spelling*
but the two int→float promotion sites matched stored bit patterns, so a
digit landing on `INT32_MAX`/`INT32_MIN`/`INT32_MIN+1` was widened as if it
were `0I`/`0N`/`-0I`. Promotion now goes by the token's own text — digits
keep their value (including past-i64 strings: `99999999999999999999 1 2 3.0`
is `1e+20 ...`), sentinel spellings keep their meaning — matching the
reference, where `2147483647 1 2.0` is `2.147484e+09 1 2`. `t775`.
- `0$` and `0j$` parsed only bare digit strings, so `0$"-5"`, `0$" 12 "`,
and `0$"0N"` were domain errors while `0.0$`
accepted all three. String→int now takes an optional `-`, surrounding
blanks, and the `0N`/`0I` spellings; junk, `+`, and floats are still
`domain`. `t776`.
- Negative overflow saturated to the *null*: `0$"-4000000000"` gave `0N`
(the high side correctly gave `0I`), and `-99999999999999999999j` — or
`strtoll`'s clamp anywhere — gave `0Nj`. Low saturation is `-0I`/`-0Ij`
everywhere now, matching the i32 lexer clamp and the reference; the null
pattern is reserved for the `0N` spelling and parse failure. Reaches `0:`
fixed-width `I`/`J` fields too. `t776`.
- `0.0e$` parsed with the f64 reader, so `"3.5e"` and `"0ie"` — the f32
printer's own output — both came back `0ne` (failure masked as null).
A real (f32) reader now takes what the lexer takes: the `0ne`/`0ie`/`-0ie`
spellings and a trailing `e` reached through a decimal point or exponent
(`"1e0e"`, `"2.147484e+09e"`), in `0.0e$` and `0:` `E` fields, so printed
f32 round-trips. `"5e"` stays unparseable, exactly as `5e` is `5` then the
name `e`. `t776`.
- `0.0$` and `0.0e$` on a char vector parsed the raw payload, not a
NUL-terminated copy — the same `1:`-mmap over-read `0$`/`0j$` were already
guarded against (a mapping ending on a page boundary has no terminator
slot). Both now copy first, and trim surrounding blanks.
- Float-side parse failure was a silent null: `0.0$"12x"` gave `0n` where
  it should have been a `domain` error. `t776`.

## Part IV — Security hardening

*Two remotely-triggerable code-execution paths through deserialization, closed at the trust boundary.*

<a id="db-confuse"></a>

#### a hostile `db` payload could forge a value type (RCE)

Deserializing an untrusted IPC message body, `db` OR'd the wire subtype into the
reconstructed K without bounding it — read as a full `i32` rather than the 8-bit
field it is. A hostile blob could set bits into the K's *type* field, forging a
value with an attacker-controlled pointer: a crafted int atom became a fake heap
vector pointing at `0x1`, and the first refcount or traversal dereferenced it and
killed the server — a type-confusion primitive, not just a crash. `db` now rejects
any wire subtype outside `0..255` and shape-checks each structural route (a list
blessed as a closure or legacy projection over-read its slots) against exactly
what `serialize` emits. Legitimate values round-trip unchanged. `t766`.

<a id="db-hijack"></a>

#### an untrusted subtype could hijack control flow (RCE)

The same untrusted-subtype pattern ran deeper: a K's 8-bit subtype routes it to
apply/eval machinery that dereferences its slots as verbs, args, or scopes, and
`db` trusted every in-range subtype from the wire. The worst was `0xdc`, a
`2:`-linked C function with a raw function pointer in slot 0 — a forged `0xdc`
blob transferred control to an attacker-chosen address when applied (demonstrated
end to end); the `0xc6`/`0xc7` builtin atoms, whose payload is used directly as a
call-table index, were a second such path. `db` now whitelists the subtype to
exactly what `serialize` emits — data, a dict, an args plist, or a shape-checked
verb/function — and rejects everything else (including the interpreter's internal
parse-node tags) at the trust boundary; `bd` refuses to serialize a process-local
linked pointer. `t767` and the `linktest` `bd`-refusal check lock it in.
